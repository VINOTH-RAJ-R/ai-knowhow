1. Money uses `decimal.Decimal` because float sums drift (e.g. 0.1+0.2) and statements need exact cents. The tests compare against values like `Decimal("45.20")`, which only works reliably with exact types.

2. Only two fixed formats are tried (`YYYY-MM-DD`, then `DD/MM/YYYY`) because the tool is stdlib-only (dateutil isn't) and those two can't be confused with each other. MM/DD/YYYY is ambiguous with DD/MM/YYYY for days 1-12, so a wrong guess would silently put spending in the wrong month (the lesson marks this consequence as inferred; the notes just say "ambiguous"). Unknown formats fail loudly with a line number.

3. Categories come from `rules.json`, an ordered map of category to keywords. The first category in file order with a keyword found (case-insensitive substring) in the description wins, and no match gives `Uncategorized`. It was chosen over scoring or longest-match because it is simple and the user controls priority just by reordering entries.

4. JSON and unittest are both in the stdlib. TOML parsing (`tomllib`) needs Python 3.11 and the build machine runs 3.10, so TOML was out. YAML isn't stdlib either (my inference; the material only names the TOML/3.10 reason), and pytest is a third-party dependency, which conflicts with the stdlib-only constraint.

5. The output shows the 2,000.00 as negative spend (-2,000.00) in the `Uncategorized` column, which also drags that month's Total down. This is because spending is stored as `spent = -amount`, and a positive income row looks the same as a refund by sign, so it was deliberately not special-cased. To fix it, add a rule such as `"Income": ["salary"]` to rules.json (README documents this).

6. Unparseable date: `parse_date` raises ValueError, `read_rows` adds the line number, and `main()` prints something like `error: line N: unrecognised date 'Jan 5 2024' (expected YYYY-MM-DD or DD/MM/YYYY)` to stderr. Missing `amount` column: it prints `error: CSV missing column(s): amount (found: ...)` to stderr. Both exit with code 1 and no table is printed.

7. It was verified by running `python3 -m unittest discover -s tests -v` (14 tests, OK on the first run) and by running the CLI by hand on the sample CSVs. Beyond happy-path parsing, tests cover DD/MM not being read as MM/DD (13/02/2024), bad dates and amounts, a missing CSV column, first-rule-wins and case-insensitivity, the Uncategorized path, refunds reducing a category, comma amounts and parentheses negatives, and CLI behaviour (table output, Uncategorized column, missing file gives exit 1 with "error:" on stderr). The lesson notes the tests only cover cases the author thought of (e.g. no substring false-positive or European-number tests).

8. Logic lives in small functions (`parse_date`, `parse_amount`, `load_rules`, `categorize`, `read_rows`, `summarize`, `format_table`) with a thin `main(argv=None)` so each piece can be tested on its own. The tests import `spendsum` directly and call these functions on tiny CSVs in tests/data. Only the `CliTests` class runs the CLI as a real subprocess via `subprocess.run([sys.executable, spendsum.py, ...])`: `test_table_output`, `test_uncategorized_column`, and `test_missing_file_is_clean_error`.

9. "Uber Eats" contains the keyword "uber", and in rules.json Transport comes before Eating Out, so first-match-wins puts it in Transport. I'd add a more specific keyword like "uber eats" to Eating Out and move Eating Out above Transport in rules.json. It works because priority is simply file order, so the more specific rule is checked first; adding the keyword alone wouldn't help while Transport is earlier.

10. I would not add MM/DD/YYYY to `DATE_FORMATS`. With both DD/MM and MM/DD in the list, 03/04/2024 would still parse as 3 April and only days over 12 would fall through, so months would be silently wrong for ambiguous dates. Instead I'd convert that bank's export to ISO (or add an explicit opt-in per-file option such as a `--date-format` flag, which the lesson lists as an unweighed option), with tests built from real rows.
