2. The README says only that MM/DD/YYYY "is not supported". The code tries just two formats via strptime (DATE_FORMATS), so there is no auto-detection. The reason isn't given (can't tell from the material). Guess: 03/05/2024 is ambiguous between DD/MM and MM/DD, and guessing wrong would silently put spend in the wrong month. A strict, explicit format list fails loudly instead. The "13/02/2024" test shows DD/MM is the intended reading.

3. Rules come from rules.json in file order. A transaction goes to the first category with any keyword that is a case-insensitive substring of its description, and no match gives "Uncategorized". Priority is changed by reordering entries. The material doesn't say why this beat scoring or longest-match (can't tell from the material). Guess: first match is simple, predictable and fully under the user's control.

4. Neither choice is explained (can't tell from the material). The README does say "Python 3, standard library only". Guess: json and unittest are both in the stdlib, while YAML, TOML (before Python 3.11, and only for reading) and pytest are not. Using them would add a dependency or an install step.

5. The row lands in "Uncategorized" as a negative number, -2,000.00, and drags that column's total and the month's Total negative. The reason is that spent = -amount, so a positive amount with no matching rule looks like negative spend. To fix it, add a rule such as `"Income": ["salary"]` to rules.json. This separates it from real spending, though it still shows as negative under Income.

6. An unparseable date raises ValueError with the line number. The user sees something like `error: line 2: unrecognised date 'Jan 5 2024' (expected YYYY-MM-DD or DD/MM/YYYY)` on stderr, and the exit code is 1. A missing 'amount' column gives `error: CSV missing column(s): amount (found: ...)`, also on stderr with exit code 1. Neither case prints a partial table, because main() catches OSError/ValueError before printing.

7. The material doesn't describe how it was verified beyond the test suite itself. It is run with `python3 -m unittest discover -s tests -v`. Beyond happy-path parsing, the tests cover DD/MM not being read as MM/DD, a bad date, a bad amount, a missing column, a refund reducing its category, first-rule-wins and case-insensitivity, the Uncategorized fallback, comma amounts and mixed month grouping. The CLI tests check exit code 0 with table output, and a missing file giving exit code 1 with "error:" on stderr.

The code is split into small functions (parse_date, parse_amount, load_rules, categorize, read_rows, summarize, format_table). main(argv=None) is a thin wrapper that parses arguments, catches errors, prints and returns an exit code. The stated reason isn't in the material, but the structure makes unit testing easy. The unit tests do `import spendsum` and call the functions directly with the fixture CSVs in tests/data. The three CliTests (test_table_output, test_uncategorized_column, test_missing_file_is_clean_error) run spendsum.py as a real subprocess via sys.executable.

9. "Uber Eats" contains "uber", and Transport is listed before Eating Out in rules.json, so Transport wins as the first match. The current Eating Out keywords (cafe, restaurant, pizza) don't match it either. I would add "uber eats" to the Eating Out keywords and move Eating Out above Transport in rules.json. The fix works because categorisation is first-category-in-file-order wins, so the more specific category must come first. Plain "Uber trip" rows still fall through to Transport.
